# SportKarta / Играй Навън — Development Plan v2 (Self-Hosted, Claude Code Desktop App)

Supersedes v1. Changes: **self-hosted stack** (no managed platform dependencies), **GitHub-driven deployment**, workflow adapted to **Claude Code in the Claude desktop app on macOS** (no terminal use by the operator — Claude Code executes all shell work inside sessions).

This file must live in the repo as `docs/ROADMAP.md`. Every Claude Code session reads it.

**Assumptions:** one operator driving Claude Code ~15–20 h/week from the desktop app; one Linux VPS (EU); NGO budget (~€15–25/mo infra); Bulgarian-first product; Sofia + Plovdiv + Varna at launch. Timeline unchanged: ~26 weeks full platform, public map MVP week 6.

## 0. Fixed technical decisions (v2)

| Layer | Choice | Why / tradeoff |
|---|---|---|
| App framework | Next.js (App Router) + TypeScript, `output: "standalone"` | SSR for programmatic SEO; standalone output = clean Docker image |
| Database | PostgreSQL 16 + **PostGIS**, self-hosted in Docker | Geospatial is the core domain. You own the data end-to-end |
| ORM | Drizzle + raw SQL for geo | Unchanged from v1 |
| Auth | **better-auth** (self-hosted): email OTP + optional Google OAuth | No auth vendor; schema lives in your Postgres. Google login is optional and can be disabled for zero external identity deps |
| File storage | Local Docker volume + `sharp` processing, storage adapter interface | No S3 vendor. Adapter keeps a later MinIO/S3 move trivial |
| Jobs/queue | **pg-boss** (Postgres-backed) + worker process in compose | Reminders, digests, imports — no Redis, one database to operate |
| Map tiles | **Protomaps** `.pmtiles` (Bulgaria extract), self-served + MapLibre GL | Fully self-hosted vector basemap — zero tile-service dependency, fast, tiny ops cost |
| Email | SMTP via env (commodity protocol, provider-agnostic) | See "external surface" below — deliverability is the one place pure self-hosting punishes you |
| Analytics | **Umami** self-hosted (compose service) | Cookieless, GDPR-clean |
| Errors | **GlitchTip** self-hosted (Sentry-compatible SDKs) | Lightweight alternative to self-hosted Sentry |
| Reverse proxy / TLS | **Caddy** in compose | Automatic Let's Encrypt, dead-simple config |
| Hosting | One Linux VPS (e.g., Hetzner CX/CAX, EU) running Docker Compose | Full control, EU data residency (a real asset in ММС conversations) |
| Deployment | **GitHub Actions → build image → GHCR → SSH deploy step → `docker compose up -d`** on the VPS | Push to `main` = deploy. All server operations run from CI, never from the operator's terminal |
| CI | GitHub Actions: typecheck, lint, unit, Playwright vs preview compose | Unchanged in spirit |
| Local dev | Docker Desktop (or OrbStack) on the Mac; Claude Code runs everything via compose | One-time GUI install by the operator; after that Claude Code drives it |
| Repo/GitHub auth | **GitHub Desktop** app for one-time sign-in + publish | Populates macOS keychain git credentials so Claude Code's `git push` works with no terminal auth dance and no tokens pasted into sessions |
| Mobile | PWA first; native only on Stage 7 evidence | Unchanged |

**Honest external-surface statement (decide once, eyes open).** "No external services" in absolute terms is impossible; here is the residual surface: GitHub (repo + CI — you asked for it), the VPS provider (rented hardware, not a SaaS lock-in; migrate with `docker compose` + backups in an afternoon), Anthropic (Claude Code itself), an SMTP relay for transactional email (swappable commodity; a fully self-hosted mail server is possible but IP-reputation/deliverability pain for OTP codes is real — revisit post-launch if you insist), and optionally Google (only if Google login stays enabled). Everything else — DB, auth, storage, tiles, analytics, errors, jobs — runs on your box.

**Legal constants (still binding; ONE amendment — see below):** ODbL attribution for OSM-derived data everywhere; open publication of the combined dataset; GDPR/ЗЗЛД: DOB derived-then-discarded, no PII in logs/exports, photos of facilities not people, cookieless analytics.

**Amended 2026-07-25 (operator decision): "minors never on individual public leaderboards" is WITHDRAWN.** Minors are treated as adults: migration `0020_minors_as_adults` dropped the `users_minor_profile_not_public` CHECK and the `is_minor` predicate from `leaderboard_eligible_members`, and the same commit removed the read-path and application guards. The remaining gate on any public individual exposure is CONSENT — the member's own opt-in, default private — which is unchanged and still enforced in the view. `is_minor` is still derived and the DOB still discarded; the flag now gates nothing. Three things the operator should note as follow-ups rather than assumptions: (a) the profile and leaderboard copy no longer promise an age-based exclusion, and the privacy page's `accountsBody` now says the age category restricts nothing (it never claimed an exclusion, so nothing there was retracted); (b) consent from a child is a guardian's to give under ЗЗЛД/GDPR Art 8 — a question for the lawyer item in the MANUAL STEPS, not for the schema; (c) `is_minor` now has no consumer, so the DOB question survives only for a possible future youth figure in the ММС annex (`lib/src/reports/grant.ts`) — if the operator does not want that figure, the honest next step is to stop asking for the date at all rather than keep collecting it. Municipality accountability = data + methodology, provenance on every record. Self-hosting on an EU VPS strengthens the data-sovereignty story — use it in ministry conversations.

## 1. Claude Code operating model (desktop app)

**Where work happens.** All development runs inside Claude Code sessions in the desktop app's Code tab, pointed at the local repo folder. The operator never opens Terminal: git, docker, pnpm, migrations — Claude Code executes them via its own shell inside the session. Manual operator actions are limited to GUI apps (Finder, GitHub Desktop, Docker Desktop, browser dashboards) and are listed explicitly at the end of any session that needs them.

**Sessions.** One prompt = one session. Start a **new session** per prompt (the app equivalent of `/clear`). Set the session model to **Fable 5** for architecture, geospatial logic, and security-sensitive work; a faster model is acceptable for mechanical batch work (translations, boilerplate). Every build prompt enforces *plan first → operator approves → implement*; if the app's plan mode toggle is available, use it, but the textual contract in each prompt is the binding mechanism.

**Project config is file-based and identical to terminal Claude Code** — CLAUDE.md, `.claude/settings.json` (permissions), `.claude/hooks`, `.claude/agents/*` all live in the repo and work the same in the app. Session 0.2 creates them.

**CLAUDE.md skeleton (Session 0.1 creates, every stage-close updates):**
```markdown
# SportKarta
NGO platform: national map of free public sports facilities in Bulgaria
+ pickup sessions + gamified sports passport. Bulgarian-first (bg default).
Self-hosted stack. Operator works ONLY through Claude Code desktop app —
never instruct them to run terminal commands; run them yourself, and put
GUI-only steps (Finder, GitHub Desktop, browser) in a MANUAL STEPS list.

## Commands (run them yourself)
- pnpm dev / build / lint / typecheck / test / test:e2e
- docker compose -f compose.dev.yml up -d   (local Postgres+PostGIS, Umami, GlitchTip)
- pnpm db:migrate / db:seed / import:osm

## Architecture
- Next.js App Router standalone; server components default
- Drizzle schema in /db/schema; geospatial = raw SQL in /db/geo
- EPSG:4326 everywhere; geometry(Point,4326); GIST indexes mandatory
- better-auth for auth; pg-boss for jobs (worker in /apps/worker)
- Storage adapter interface in /lib/storage (local-volume impl)
- Tiles: self-served pmtiles at /tiles; MapLibre style in /apps/web/map
- i18n: next-intl; NEVER hardcode UI strings; bg source of truth

## Rules
- Provenance on every facility record; crowd-verified fields never
  overwritten by imports (merge policy: crowd > municipal > osm)
- OSM/Protomaps attribution on every map view and export
- No PII in logs; no identifiable people in photos
- Public individual exposure requires the member's own opt-in (age is not a
  condition — the minors exclusion was withdrawn 2026-07-25, migration 0020)
- Migrations forward-only, reviewed by db-migration-reviewer subagent
- Deploys happen ONLY via GitHub Actions on main — never deploy from a session
```

**Permissions (`.claude/settings.json`).** Allow without prompting: pnpm lint/typecheck/test/build, git status/diff/log/add/commit/push, docker compose against `compose.dev.yml`. Require approval: migrations against non-local DATABASE_URL, `docker` against prod compose file, `rm -rf`, reading `.env*`. Prod credentials exist only as GitHub Actions secrets and on the VPS — never inside sessions.

**Hooks.** PostToolUse (Edit/Write on `*.ts,*.tsx`) → typecheck + lint --fix. Pre-commit → unit tests on changed packages. SessionStart → print branch + first unchecked ROADMAP item.

**Subagents.** Same four as v1: `code-reviewer` (adversarial: authz, PII, SRID/GIST correctness, i18n misses), `db-migration-reviewer`, `osm-data-auditor`, `test-writer`.

**Automation without a terminal.** Anything v1 ran headless (`claude -p`) becomes either (a) a scheduled GitHub Actions workflow, or (b) a recurring paste-prompt run in the app (default for the weekly QA). CI is the operator's remote hands: deploys, scheduled jobs, and backup verification all run from Actions.

- [x] **3.2 Contribution flows + points** — authenticated add (photo required, geolocated pin with manual adjust, 30 m duplicate guard, lands `needs_verification`/`source=crowd`), structured verify checklist, and condition reports (`отлично|добро|лошо|неизползваемо` + closed tag vocabulary + optional photo) — all writing through `facility_edits` with the account id as `actor` (migration `0006_contributions_points`). "It is gone" files a moderation report rather than deleting, and earns nothing. `points_ledger` is append-only and idempotency-keyed: one award per facility added, per person per facility verified, per person per facility per Sofia day for conditions, proven under concurrency and random retry interleavings in `db/src/points-ledger.test.ts`. - [x] **3.3 Ambassadors + moderation v2** — roles collapse to `user | ambassador | admin` (`moderator` retired and CHECK-forbidden, migration `0007_ambassadors_moderation`). Ambassadors moderate photos, reports and crowd `needs_verification` facilities **only in the municipalities granted to them**, and the scope lives in the SQL: every mutation joins `ambassador_municipalities`, so an out-of-scope decision updates zero rows even with the application bypassed — proven at the query layer in `db/src/moderation-authz.test.ts`. Every decision lands in the append-only `moderation_decisions` log (opaque actor id, scope frozen at decision time, `queued_at` for SLA). Admin screen at `/admin/ambasadori` grants/revokes role and municipalities and shows per-ambassador activity; the moderation screen gains median time-to-decision, queue depth and oldest-waiting. Weekly assistive pre-screen: `docs/prompts/moderation-prescreen.md` + `pnpm mod:queue` (read-only) and `pnpm mod:flag` (writes `moderation_flags` and nothing else) — flags only, a human decides.
- [x] **3.4 Municipality accountability pages + embeddable aggregate-only widget** — `/obshtina/[city]` publishes coverage (per 10 000 residents, ranked only among municipalities that HAVE an NSI population figure — the rest get "n/a" and are left out, never estimated), data quality, the public's own condition reports, provenance, and time-to-decision on problem reports. That last number **measures us, not the municipality**, and the page says so in as many words: publishing a responsiveness metric that quietly blames a mayor's office for our own moderation backlog loses the argument the first time somebody checks. Every figure uses the public map's visibility rule (`status <> 'gone' AND slug IS NOT NULL`), so a municipality can count the pins on `/igrishta/[city]` and get the same number — a metric nobody can reconcile is a metric nobody believes. **Aggregate-only is a property of the TYPE, not of the page**: `MunicipalityAccountability` has no field that can hold a person, and the gate has two stages that only work together — the test fixture is annotated with the interface, so adding `topContributor: string` breaks `typecheck` until it is added to the fixture, at which point the shape test fails because it is a string outside the six place-identifying fields. Contributor *counts* are k-suppressed below 5 (null means "1..4", so no second boolean field needs an exception carved for it). The widget is a **route handler, not a page**, deliberately: pages under `[locale]` inherit the layout that registers a service worker and loads Umami and GlitchTip, and embedding us must not make a municipality's visitors subject to our telemetry when there is no consent banner inside an iframe. It serves a self-contained document with `script-src 'none'`, no cookie, no external request, inline CSS, and ODbL attribution rendered unconditionally; `?format=json` returns the same payload CORS-open. Adding one frameable surface meant denying the rest, so `next.config.ts` now sets `X-Frame-Options: DENY` + `frame-ancestors 'none'` everywhere except `/api/widget` — via a negative lookahead rather than rule ordering, because which CSP survives two overlapping `source` entries is not a thing to leave to precedence. `e2e/accountability.spec.ts` asserts the envelope a unit test cannot see: the deny is present on the page, absent on the widget, and no `Set-Cookie` on either.

## 6. Stage 4 — Play layer (Weeks 9–14)

Sessions schema with RRULE recurrence, rolling 8-week occurrence materialization via pg-boss, Europe/Sofia DST property tests (non-negotiable); RSVP/waitlist, tokened iCal, idempotent T-24h/T-2h reminder emails through the SMTP abstraction; organizer tools with signed expiring QR check-in; weekly city digest page + opt-in email; admin bulk-create for the сдружение's official slots; results v1 with CSV import. No timing hardware.

- [x] **4.1 Sessions schema + recurrence engine** — schema and logic only, no UI (migration `0008_play_sessions`; tables are `play_session*` because better-auth owns `sessions`). A session is scheduled in **wall clock** time: `starts_at_local` is `timestamp` without time zone and the RRULE is expanded in pure civil arithmetic (`lib/src/recurrence`), so a weekly 18:00 session is 18:00 in January and in July while the UTC instant moves. The rule grammar is a deliberate subset — `FREQ=DAILY|WEEKLY`, `INTERVAL`, `BYDAY` (weekly only), `COUNT` xor `UNTIL`, `WKST=MO` — rejected at parse time *and* by CHECK constraints, so no writer can store a rule the engine cannot expand. DST policy is explicit and recorded per occurrence in `dst_resolution`: the vanished March hour shifts forward (`gap_shifted`), the repeated October hour takes the earlier instant (`fold_first`). Property tests discover every Bulgarian transition 2020–2035 from the tz database rather than hardcoding dates (`lib/src/recurrence/dst.test.ts`), and a trigger cross-checks every materialized row against PostgreSQL's own tzdata. Occurrences are written **only** by the `session.materialize` pg-boss job over a rolling 8-week window, idempotent via `INSERT … ON CONFLICT DO NOTHING` on `(session_id, starts_at)`. RSVP stores **order only** — an arrival ticket per row, position from `row_number()`, going/waitlisted derived in `play_session_rsvp_positions` — so over-booking is impossible (no counter to race on) and a withdrawal promotes the next person with no code running (`db/src/sessions-waitlist.test.ts`). Cancelling a series cancels its *future* occurrences only; the past is never rewritten. Erasing an organiser nulls `organizer_id` and a trigger cancels the series, preserving other people's attendance — and nothing here can block a `DELETE FROM users`. Cancellation notification is stubbed to the `session.notify` queue (counts, never addresses) for 4.2.
- [x] **4.2 RSVP notifications, tokened iCal, T-24h/T-2h reminder emails** — migration `0013_session_notifications`. **The reminder job does not ask "starting in 24 h ± 5 min"**; it asks "starting within the lead time and NOT YET TOLD", against the `play_session_notifications` ledger. The window query mails *nobody at all* for any session whose window the job slept through — a deploy, a restart, a slow queue — and leaves no evidence that it did not; the ledger version is self-healing after downtime and cannot double-send however often it runs. The ledger carries **two partial unique keys**, and the db-migration-reviewer is why: three of the six kinds are re-entrant, because 4.1 lets a member withdraw and re-join for a fresh arrival ticket. Under one flat key, somebody who withdrew, re-joined the waitlist and was let back in would **never be told they were in** — silently, with the ledger insisting they had been. So RSVP-scoped kinds key on the ticket and occurrence-scoped kinds key on NULL, bound by a CHECK; keying reminders by ticket would instead re-send "24 hours to go" to anyone who re-joined. The same review caught a **lock-order inversion**: FKs on `users` before the `account_deletions` block deadlocks against `apps/web/lib/account-deletion.ts`, and `deadlock_timeout` (1 s) fires before `lock_timeout` (3 s), so a deploy overlapping a GDPR erasure aborts one of them — 0012's ordering is now restored and stated in the header. Promotion has **no event to hook** (4.1 promotes by arithmetic, with no code running), so `withdraw` diffs who was going either side of the update inside one transaction; concurrent withdrawals may compute overlapping sets and that is deliberately unlocked, because the ledger dedupes the send. **Nothing is sent from a request**: actions enqueue `session.notify` with occurrence ids and ACCOUNT ids — never an address, since a job row outlives the account it names — and the worker resolves the inbox at send time, claiming the ledger inside the transaction, before the SMTP handoff. iCal (`lib/src/ical`) emits **UTC instants and no VTIMEZONE at all**: a hand-written Europe/Sofia VTIMEZONE would be a second copy of the DST rules 4.1 went to such lengths to have exactly one of. Folding is at 75 **octets** over whole code points — Bulgarian is two bytes a letter, so a character-counting folder emits over-long lines and a naive byte-counting one puts mojibake in the middle of every session title, and neither failure throws anywhere. Cancelled occurrences stay in the feed as `STATUS:CANCELLED` with a bumped `SEQUENCE`, because a client that merely stops seeing an event may keep showing it. The feed token is a **credential** (a calendar client cannot sign in): one row per member so rotation kills every copy of the old URL at once, `private, no-store`, `noindex`, a flat 404 for unknown *and* malformed tokens, and a CHECK that it is not the account id — better-auth ids match the shape rule, so without it a regression would hand a live session subject to every calendar server that polls us. The new public session page names the organiser and **no attendee at all**: 0008 left that to the UI, and a public page naming people next to a place and a recurring time publishes where they reliably are on a Tuesday.
- [x] **4.3 Organizer tools + signed expiring QR check-in** — completed in two halves: the signed expiring QR shipped inside 5.4 (it could not be demonstrated without it), and the rest — the roster/manual check-in deck and per-occurrence organiser controls — shipped 2026-07-25. **The roster is the one sanctioned crossing of the no-names line**: `play_session_rsvp_positions` deliberately carries no display name, the public occurrence page shows counts only, and `apps/web/lib/sessions/roster.ts` joins the view to `users` ONLY behind the same organiser-or-admin SQL gate the QR screen uses — display names and nothing else (no email, no role, and deliberately no minor flag: marking which attendee is a child on a screen held up in a park would disclose exactly what the minors rules protect). QR walk-ins — checked in, never RSVPed — get their own section, because attendance is a fact wherever it came from. Manual check-in reuses `checkIn(method:'organizer')`: a vouch, recorded, NEVER scored (the 0014 CHECK, not code), `recorded_by` names the voucher, idempotent under a double tap — **and hardened by this stage's code review**: the reviewer showed the organiser gate alone let an organiser fabricate an attendance row for ANY account id in the system, rows that flow unfiltered into the named person's passport history, streaks and retroactively-awarded badges. A vouch may now name only a member holding an active RSVP on the occurrence (`not_attending` otherwise, decided in the same context statement), which also converts the stale-roster-row-for-an-erased-account 500 into a clean refusal. The check-in window is one shared SQL fragment (`checkinWindowSql`) embedded by both `checkIn` and the roster gate, so the deck's buttons and the domain function cannot drift apart. **The deck never offers a button the domain function would refuse**: it asks the DATABASE's clock the same window question `checkIn` asks (`checkin_open` via `make_interval`/`now()` in the gate query), hides the buttons outside the window and says when check-in opens — found live, when a button on a 2027 fixture failed silently. The occurrence page's organiser box (organiser only — an admin uses the gated pages directly) links the deck and the QR screen and wires the two cancellation functions 4.2 left waiting (`cancelOccurrence`/`cancelSeries`, organiser-or-admin re-authorized in SQL, notice deduped by the 0013 ledger) behind `ConfirmButton`, fire-and-forget like every admin one-click op — the re-rendered page is the feedback. Roster deck matches the QR screen's envelope: self-gated 404 for outsiders, no AppShell, `<meta refresh>` instead of client JS so QR redemptions surface while the phone sits on a bench. Tests: `apps/web/tests/roster.test.ts` (statement level: the gate is asked of the database, nothing is read past a refusal), `db/src/sessions-roster.test.ts` (real Postgres: queue order + names, walk-in anti-join, the only-qr-scores CHECK, double-tap idempotency). Verified live in the browser as the audit organiser: mark-present wrote `method='organizer', scored=false, recorded_by=<organiser>`; cancel-occurrence set `cancelled/occurrence` and left the series scheduled. Deliberately NOT built: member-facing session creation/editing UI — `createSession`/`updateSession` sit ready in `apps/web/lib/sessions/sessions.ts`. **Operator decision (2026-07-25): members WILL be able to create sessions, gated behind an achievement threshold** — tracked as 4.7 below.
- [ ] 4.7 Member session creation behind an achievement gate — operator decision 2026-07-25: an ordinary member unlocks "create a session" only once certain achievements are reached (threshold TBD — candidates: a badge from the `lib/src/badges` catalogue, a points floor in `points_ledger`, or N verified contributions; the badge fold is the natural gate since badges are already derived, retroactive and config-driven). The domain functions exist (`createSession`/`updateSession` in `apps/web/lib/sessions/sessions.ts`); the work is the gate predicate, the create/edit UI (rrule subset editor), and the i18n. Deferred by the operator — "we will fix this a bit later".
- [x] **4.4 Weekly city page + opt-in digest email** — `/sedmitsata/[city]` and the Monday email are the **same query**, `weeklyDigest` in `@sportkarta/db`, so what a member reads in the mail is what they find when they follow the link (`apps/web/tests/digest.test.ts` asserts it rather than documenting it). The week is a Sofia wall-clock Monday→Monday, so the DST weeks are 167/169 h and still start at midnight. Opt-in is signed-in members only, per city, and one-click unsubscribe works **without a session** — but the GET only renders a confirm button, because Safe Links and Proofpoint fetch every URL in an inbound mail and a destructive GET would unsubscribe exactly the people whose employer protects them. Sending is idempotent through `digest_sends` (claim inside the transaction, before the send), so a retry or a second worker cannot mail anyone twice; scheduled `0 8 * * 1` with `tz: 'Europe/Sofia'` so the send time does not drift twice a year. Logs are counts and error *categories* — never an address, since an SMTP rejection embeds the recipient in its message.
- [x] **4.5 Admin bulk-create** — `/admin/sesii`, `requireRole('admin')` on the page and every action. The primary path is the real task: describe one slot, filter the facility list, tick, submit once. The CSV path adds column mapping (auto-guessed from Bulgarian or English headers) and a validation preview. **Valid rows commit, invalid rows are skipped and listed with a row number and reason** — a 200-row file with three typos creates 197 sessions instead of being rejected. A file with an unterminated quote is refused outright, because the rows it can see are not the rows in the file.
- [x] **4.6 Results v1 + CSV import** — one row per participant or side (`play_session_results`, migration `0009_digest_results`), covering a football scoreline and a 5 km run with one shape. **NO TIMING HARDWARE**, stated in the migration header, the column comment and the admin screen: no device id, no chip/gun/net time, no timing-system import, and `score` is text an organiser typed. Erasing a participant anonymises the row rather than deleting it — a result is a fact about a game other people played in too — which is why "a result identifies somebody" is a BEFORE INSERT trigger and not a CHECK (as a CHECK, the `ON DELETE SET NULL` would abort `DELETE FROM users` forever). Re-saving never destroys those anonymised rows and never writes a member's name into the free-text label.

## 7. Stage 5 — Спортен паспорт (Weeks 14–18)

Passport profile, declarative badge engine (config, not schema changes), DST-correct streaks; leaderboards with minor protection enforced at the query layer and attacked in tests; challenges as config with admin CRUD and a full staged demo campaign; QR/geofence-verified scoring, proportionate anti-abuse.

- [x] **5.1 Passport profile + declarative badges + DST-correct streaks** — badges are **derived, not granted**: the database contributes one flat `PassportEvent` stream (points_ledger + play_session_checkins) and every rule is a pure fold over it in `lib/src/badges`. That is what makes "config, not schema changes" true a year from now — migration `0010_passport` contains no badges table, no badge enum and no threshold column, so a new badge is one entry in `catalog.ts` plus two i18n keys. Because the fold walks history rather than watching for new events, a badge added later is awarded **retroactively with the date it would really have been earned**; `user_badges` exists only to record whether the member has been *told*, and is never read to decide whether a badge is held. Ten launch badges, six contribution and four participation. Contribution rules count **awarded ledger rows**, so Stage 3.2's idempotency keys are the anti-farming layer for free. Streaks are consecutive **civil** Sofia days and Monday-start weeks: the two DST days are 23 h and 25 h long, so every successor is `addDays` on a wall clock and no instant is ever added to — property-tested against every Bulgarian transition 2020–2035 discovered from the tz database, not hardcoded (`lib/src/badges/streaks.test.ts`). The public passport at `/pasport/<handle>` is **opt-in, minor-locked and aggregate-only**: badges dated to a month, totals and streak lengths, never a facility, a day or a time, because a public page tying a named person to a place and a moment publishes where they reliably are. `users_minor_profile_not_public` is written as an allowlist so a future visibility value stays forbidden until deliberately permitted, and the handle is random rather than the account id, which is the better-auth session subject. noindex and absent from the sitemap — "public" means "anyone I send the link to", not "indexed against your name forever".
- [x] **5.2 Leaderboards (national, per city, per sport) with minor protection at the query layer** — the operator resolved the Stage 3.2 tension: leaderboards ship, and CLAUDE.md now says so. Who may appear is defined **once**, in the `leaderboard_eligible_members` view (migration `0011_leaderboard`), and every ranking joins that view instead of `users` — so the national, per-city and per-sport boards cannot disagree about the rule, and the fourth slice somebody adds next year inherits it without its author knowing the rule exists. Two conditions: **not a minor** (the binding legal constant — and 0010's CHECK already makes a public minor unconstructible, so the protection is two independent layers, which `db/src/leaderboard-authz.test.ts` proves by trying and failing to build the dangerous fixture), and **has opted their passport public** — appearing on a ranked public list publishes a name next to an activity level, and members who joined before this existed never agreed to that, so the board is a ranked index of passports people chose to publish rather than a census of the membership. Ranked on `points_ledger`, whose idempotency keys were designed not to be gameable before anything ranked them; check-ins are deliberately **not** ranked, being self-attested until 4.3's signed QR exists. Ties share a rank. All-time and current-Sofia-month periods. noindex, like the passports it links to — indexing it would undo 0010.
- [x] **5.3 Campaign engine: config-driven scoring, admin CRUD, frozen close-out** — "campaigns as config" and "admin CRUD" only reconcile if you are precise about which part is config. A campaign is a **row** (an admin creates one from a browser without a deploy); what stays config is its **`rules` JSONB document**, validated against a closed grammar in `lib/src/campaigns` and compiled to one weighted SQL aggregate in `db/src/campaigns.ts`. Creating a campaign is a form; inventing a new *kind* of scoring is a grammar change with a deploy and a test. Date-bounded in **civil** Sofia time (`ends_on` inclusive as authored, exclusive as compiled — that off-by-one silently discards the last and busiest day), scoped national/city/quarter with coherence CHECK-enforced, weighted over ledger + check-in events, with a **per-day cap** — the first feature where gaming the ledger wins a *prize*, so the cap and the ledger's existing idempotency keys are the anti-abuse layer. Two board types: `individual` names only adults with a public passport, while `city` names nobody and therefore **counts everyone including minors**, with municipalities under `CITY_BOARD_MIN_MEMBERS` suppressed (a city row backed by one person is that person's score wearing a city's name). Scoring always counts everyone and only *display* is gated, so a member who never opted in can still win; the admin board shows real names because somebody has to hand over the prize. **Closing FREEZES the standings** into `campaign_results` — a results page that recomputes changes after prizes are announced — but freezes *no display name*: identity resolves live through the 0011 view, so an erased or newly-private member keeps their placing and loses their name. Migration `0012_campaigns`; `campaigns_rules_shaped` is written with `CASE` rather than `AND` because `TRUE AND NULL` is NULL and **a CHECK passes on NULL**, so the obvious conjunction would have accepted `{}` and a misspelled key.
- [x] **5.4 QR/geofence-verified scoring + proportionate anti-abuse** — migration `0014_qr_checkin`. **The honest statement first, because a dishonest one here would be worse than the feature:** the QR token proves somebody could read the organiser's screen in the last two minutes, not who; the geofence uses coordinates the BROWSER supplied, which anyone determined can fake in a minute. Neither is proof, and `lib/sessions/checkin.ts` says so in as many words. What they are is a *cost* — to farm attendance you must obtain a fresh token every two minutes from a session you are not at and lie about your location, for two points, capped at three a day. That is the whole of "proportionate"; the alternatives (a device id, background location, a photo) all collect far more about children than the problem justifies. **`distance_m`, never coordinates**: the browser's reading lives for one SQL statement, is compared against a facility location we already publish, and only the metres are stored — storing lat/lon would build a record of where named children stand on Tuesday evenings, and `db/src/checkin-scoring.test.ts` asserts against `information_schema` that no column could hold one. **Only a QR check-in may score, as a CHECK** (`play_session_checkins_only_qr_scores`): Stage 5.2 ranked points and not check-ins precisely because check-ins were self-attested, and this keeps that true now that some of them are not — `self` is a button somebody tapped, `organizer` is somebody vouching, both are recorded and neither is evidence. The token is **windowed, not timestamped** (`floor(now/60s)`), so the QR is stable under a camera, verification needs no issued-token table, and replay decays by arithmetic rather than revocation; the signature is checked BEFORE the clock and with `timingSafeEqual`, so expiry is not an oracle, and every failure — forged, expired, wrong session, no secret — reads identically to the member. Its separator is `~` rather than `.`, because `middleware.ts` skips any path containing a dot and a dotted token would silently 404. **Nothing on the anti-abuse list refuses a check-in**: attendance is a fact and is always recorded, only the payment stops — an anti-abuse rule that can wrongly erase a child's attendance is worse than one that can wrongly decline two points, and only the second has an appeal path. The organiser screen carries **no client JavaScript** (server-rendered SVG + `<meta http-equiv="refresh">` timed to the window end), because a React interval dies when a phone sleeps or park wifi eats the bundle. `CHECKIN_TOKEN_SECRET` unset or under 32 characters disables QR check-in entirely rather than accepting anything.
  - **From the db-migration-reviewer, and each one changed the code:** (1) the `distance_m` upper bound could *refuse a check-in* — a desktop browser falling back to an IP-derived fix is a continent from Sofia, which would have raised SQLSTATE 23514, aborted the transaction and recorded no attendance at all, directly contradicting the invariant the stage rests on; the writer now clamps with `least(…)` so a constraint never decides whether somebody's attendance exists. (2) The header's GDPR argument was *wrong on its facts* — `qr_has_no_recorder` does name `recorded_by`, which is `ON DELETE SET NULL`, so erasing an organiser DOES re-evaluate all four CHECKs; it is safe only because the predicate is **monotone** under that update, and the header now says so, with an explicit warning that tightening it into the obvious equivalence would abort `DELETE FROM users` forever. (3) The locking claim was false: `ADD CONSTRAINT` takes ACCESS EXCLUSIVE on a table the erasure path both reads and cascades into. (4) The "two migrations" enum rule 0013 recorded does not hold — `drizzle-kit migrate` wraps *all pending* migrations in one transaction, and a from-scratch database permits the new value, so the mistake would be green in CI and `db:reset` and fail only in production; the real rule is a separate `db:migrate` **invocation**, corrected in both headers. (5) `db/src/campaigns.ts` scored `session_checkin` with no method filter, so a self-attested tap already counted toward a campaign **prize** — now filtered to `method = 'qr'` (on the method, not `scored`: a capped or location-less attendance is still verified attendance).
  - **Also fixed here:** next-intl reads a dot in a key as nesting and rejects the catalogue at *request* time; the i18n parity test flattens with dots and so could never see the difference. `apps/web/tests/i18n.test.ts` now refuses any literal key containing a dot.
  - **Test-suite fix found on the way:** the new property suites tipped `lib`'s already-borderline fast-check tests (the tz-database DST discovery among them) past Vitest's 5 s default when the package runs in parallel — an intermittent failure that trains people to re-run rather than read. `lib/vitest.config.ts` now sets `testTimeout: 30_000` instead of shrinking the properties, since the number of random cases is the value. `foldLine` also stopped allocating a typed array per character.
  - **Still open from 4.3:** the rest of the organiser tooling — a roster/manual check-in deck and per-occurrence organiser controls. The signed expiring QR that 4.3 names is built and shipped here, because 5.4 could not be demonstrated without it.

## 8. Stage 6 — Open data & institutions (Weeks 18–22)

Open data portal: documented API + nightly versioned GeoJSON/CSV dumps (ODbL + attribution), keys with soft limits, PII-denylist export tests; embeddable widget hardening; ММС-formatted grant-report exports (Bulgarian field names); quarterly national report generator with query-traceable figures; municipal CSV inbox with mapping/validation/dedupe through the merge policy.

- [x] **6.1 /danni portal: documented API, nightly versioned dumps, free keys, ODbL** — migration `0015_open_data`. **An export is a declared SCHEMA, not a query.** `lib/src/opendata/schema.ts` is a closed catalogue of datasets and fields, and the API, the nightly dump job, the documentation page and the PII denylist all read that one array — so there is no path from a column in the database to a file on the internet that does not pass through it. That indirection is the whole feature: "we tested the exports for personal data" is worth nothing when the test names three endpoints somebody remembered to add, because the fourth endpoint, written in a hurry eighteen months from now, is the one that leaks. The SELECT list is GENERATED from the declared fields, so `SELECT *` is unconstructible and a column cannot be exported without being declared, documented and scanned. The `/danni` field tables render from the same catalogue, which is what makes "a field cannot be exported undocumented" structural rather than a habit — a hand-written docs page is accurate the day it is written and quietly wrong two releases later, which for an API a municipality's dashboard depends on is worse than no documentation.
  - **The denylist is layered, weakest to strongest**, because each layer catches what the one before it cannot: (1) field NAMES may not contain a person-bearing token; (2) neither may their SQL, since `u.email AS contact` passes layer 1; (3) every relation read must be on an ALLOWLIST — the strong one, because 1 and 2 catch names somebody chose while this catches the table whatever its columns are called, **including tables that do not exist yet**; (4) no `jsonb` field, ever, `facilities.attrs` being the reason (an open bag of OSM tags, and OSM tags include `contact:phone`, `contact:email` and `operator` — no field-level review can see inside a jsonb column, so the rule is that the type is not exportable); (5) the facility export must carry the public map's own visibility predicate; (6) and, against the live database, the columns that come back must be EXACTLY the declared ones, which is the assertion no pure test can make. Tokens match on WHOLE TOKENS after splitting on non-alphanumerics, never as substrings — `municipality` contains "ip", and a substring matcher would have rejected the most important column in the dataset while appearing to work perfectly. A test asserts the matcher recognises `uploaded_by`, `organizer_id` and `users.public_handle`, and another asserts the catalogue is non-empty, because **a denylist suite that iterates an empty array is green and worthless**.
  - **The export cannot out-publish the map.** `PUBLIC_FACILITY_PREDICATE` is declared once in the catalogue, compiled once to `publicFacilityVisible`, and `apps/web/lib/public-data.ts` now builds from that same fragment. Two copies would agree on the day they were written and diverge the first time one was edited — and a facility withdrawn from the map that stayed in the nightly CSV is not a rendering bug, it is publishing something we decided not to publish. A live-DB test asks the database directly whether the export's row set is a subset of the map's.
  - **A key raises the limit and nothing else.** The data is ODbL-public and the API answers anonymous callers in full; requiring registration to read public data would be a contradiction institutions notice. So issuing is instant, free and unreviewed, an unrecognised or revoked key falls through to the anonymous budget rather than 401ing (a revoked key must not stop somebody receiving what they could have had with no key at all), and `api_keys_hash_is_sha256_hex` pins the hash column to 64 hex characters — a shape an issued key (43 base64url chars, `-` and `_` among them) **cannot satisfy**, so storing the plaintext is a constraint violation rather than a code review. Header-only `Authorization: Bearer`: no `?api_key=`, because a credential in a query string lands in every proxy log and Referer along the way; and **no session cookie**, because these responses are `Access-Control-Allow-Origin: *` and a CORS-open endpoint that honours a cookie is a CSRF surface. There is deliberately **NO request log** — an access log for this API would be a standing record of which municipality's data an identified account keeps asking about, more sensitive than anything it protects — so rate limiting is in-memory, per process, and allowed to forget.
  - **"Soft" is four properties, not a big number:** RateLimit headers on EVERY response so a client can slow down before being refused; 429 with `Retry-After` and a pointer to the bulk dump, never a ban and never an automatic revocation; **the dumps are not rate limited at all**, because the right answer to 4 000 requests an hour is the whole dataset in one file and metering the exit would leave a determined consumer no legitimate path; and it **fails open**, since an open-data API going dark because a counter threw is worse than serving too much.
  - **Dumps are versioned by civil Sofia date in the PATH**, never overwritten in place, and the `opendata_dumps` row is written only after the file is complete and hashed — the table is the index, the file is the artifact, and a directory listing would also show a half-written file mid-run. The download route serves the storage key **from the row**, so traversal is not merely blocked but unexpressible and a leftover file that was never recorded is unreachable. **Found by running the job twice and diffing:** the CSVs matched across runs and the GeoJSON did not, because it embeds `generated_at` — which breaks the `Cache-Control: immutable` on every dump URL, leaving caches serving bytes whose checksum no longer matched the manifest, invisibly. Artifacts are now stamped with the VERSION rather than the wall clock, and a regression test pins it.
  - **CSV carries no in-band attribution, deliberately.** A `# © OpenStreetMap contributors` line above the header is not CSV, and every parser that meets one either fails or reads the licence as a column name; an unparseable file with a licence inside is worse for compliance than a clean file with the licence beside it, because nobody redistributes the first. So attribution travels as `Link: rel="license"` + `X-License` + `X-Attribution` on every response, as members of every GeoJSON/JSON body, and as a `LICENSE.txt` in every dump version. The writing itself reuses `lib/src/csv.ts` (already RFC 4180 and already formula-safe, its own header naming Stage 6 as a caller) rather than a second quoter that would eventually diverge — with the coupling stated, since it treats a leading `-` as a formula leader and that is safe only because no numeric field in the catalogue can be negative.
  - **Deploy change this forced:** `apps/worker` had no `uploads` volume and no `STORAGE_DIR`, so the job would have written dumps into a container filesystem that vanishes on the next deploy — silently, since the job would report success and only the download route would 404. Both are now set in `deploy/compose.prod.yml`.
  - ~~Still open in Stage 6: widget hardening~~ — **closed 2026-07-25.** The widget's design guarantees (no script, no cookie, aggregate-only type) were already structural; what was missing was OPERATIONAL: the advertised `s-maxage` was a wish, because Caddy is a plain proxy and caches nothing, so every visitor of every embedding municipal homepage ran the accountability queries against Postgres. `apps/web/lib/widget-cache.ts` is the fix — an in-memory micro-cache (5-min fresh window, keys are municipality slugs so ≤265 entries, bounded by construction) with **stale-while-error**: through a deploy or DB restart a stale copy up to a day old keeps the embed alive, which is what the route header always promised; only a cold process with no copy degrades, to a polite 503 (`Retry-After`, `no-store`, same CSP envelope, translated message) instead of a raw error page inside a municipality's iframe. A degraded response is re-cacheable for 60 s only, so an outage cannot pin an hour-long stale copy into intermediaries. Header parity closed on the JSON variant (`Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` — the HTML variant's promises now hold for the dashboard-consumed representation too). Unit-tested with an injected clock (`apps/web/tests/widget-cache.test.ts`); the e2e envelope assertions extended to pin the new headers on both representations.

- [x] **6.2 ММС grant reports + national quarterly report** — no migration; every figure derives from existing tables. **A FIGURE IS A DECLARED METRIC**, the same shape 6.1 gave exports: `lib/src/reports/` is a catalogue where each metric is a Bulgarian label, a definition, a unit, an SQL query and two flags, and the admin annex, the PDF renderer, the printed methodology and the reconciliation tests all read that one array. A number cannot reach a ministry without its definition, its SQL and its test coming with it — a report assembled by hand is accurate the quarter it is written and quietly wrong the next, and the wrongness surfaces in a room where somebody is deciding whether to fund us. The methodology section of every rendered report prints each figure's SQL verbatim, so "where does 1 284 come from?" is answerable by somebody who has our database and not our source code.
  - **Attendance is never one number, and this is the most audit-relevant decision in the stage.** Migration 0014 carries a CHECK that only a QR check-in scores, because `self` is a button somebody tapped at home and `organizer` is somebody vouching. Reporting the three summed as "посещения" to a funder claims a figure our own schema refuses to treat as evidence — and it is the figure an auditor asks about first. So the grant annex has three separate rows, the verified one leading, and a test asserts no metric counts check-ins without filtering the method.
  - **Non-additive figures say so.** A person who plays in Sofia and Plovdiv is one participant nationally and appears in two municipal annexes; sum the annexes and you exceed the national total. Every distinct-person metric is `additive: false`, the renderer marks it (but only on a municipality-scoped report, where somebody could actually be adding annexes up — caught on the first real PDF, where a national page carried the warning pointlessly), and the reconciliation test asserts additive metrics DO sum across municipalities to the national figure while a distinct-person count is strictly less than the sum of its parts.
  - **Audience decides suppression, as a property of the REPORT.** The public quarterly report k-suppresses person-derived figures below 5 (matching the accountability pages' threshold, deliberately — two thresholds for the same disclosure would mean one is wrong); the ministry annex does not, because an annex filed under a lawful basis that hides a count of 3 is unusable for accounting and would simply be asked for again. Zero is never suppressed: "nobody did this" discloses nothing, and redacting it would make a real absence look like a redaction. A missing figure renders as an em dash, never as 0 — "not measured" is a different claim from "it was zero", and the wrong one to file.
  - **Bulgarian field names live in the catalogue, not in `messages/*.json`.** An ММС annex field name is a document format the ministry specifies, and it must read identically when an English-locale admin exports it, because the artifact is a Bulgarian document filed with a Bulgarian authority. Putting it in the i18n catalogue would make it locale-dependent and wrong exactly once — the day somebody exports in English. It also keeps `apps/web/tests/i18n-hardcoded.test.ts`'s allowlist empty.
  - **The reconciliation standard is `/statistika`'s, made to work harder.** A report metric's SQL is its own definition, so "run the metric, then run it again" is a tautology; instead `db/src/reports/reconcile.test.ts` builds a deliberately lopsided fixture (three people, four RSVPs, one check-in of each method, a cancelled occurrence) and asserts every figure against a number computed by hand, then asserts additivity, municipality scoping, the inclusive last day, and that the quarterly coverage figures EQUAL a direct query on `facilities` — so the report, the statistics page and the open-data API cannot show three numbers. The coverage-gaps table starts from `municipalities` and LEFT JOINs the stats view precisely because a municipality with zero facilities is absent from that view, and a gaps table built from it would omit the worst gaps while looking complete; a test inserts a facility-less municipality and asserts it appears.
  - **Civil Sofia periods throughout.** A quarter begins at midnight in Sofia (21:00 UTC the previous day in summer), resolved through the recurrence engine's DST-correct primitive, not by string arithmetic. Windows are half-open so consecutive quarters meet exactly — neither double-counting a session nor dropping one — and the renderer prints the inclusive last day. **Found by the rendering tests:** the first draft printed the UTC date of a Sofia instant, so a quarter covering April–June was headed "31.03 – 29.06"; every date on the document now goes through a civil-Sofia formatter.
  - **`/admin/otcheti`** (admin-only; ambassadors excluded — an annex is grant accounting, not moderation) is a GET form so a scope is bookmarkable, with a live preview from the same catalogue as the downloads. `/api/admin/otcheti?format=csv|html` serves the file, gates itself with `requireRole('admin')` reading the role from the database, and is `private, no-store` + `noindex`.
  - **`scripts/quarterly-report`** renders HTML→PDF through Playwright's Chromium (`pnpm report:quarterly [-- 2026-Q2]`, `pnpm report:grant -- --from … --to … [--municipality …]`). **No PDF is produced server-side**, deliberately: it would mean Chromium in the production image — several hundred MB and a memory spike on a €15–25/mo VPS — for a document produced four times a year. The admin HTML is print-ready for the browser's own dialog; the script produces PDFs unattended, and writes the HTML plus a clear note if Chromium is absent rather than producing nothing. Output is gitignored (dev-database figures are partial); a published report is committed with `git add -f`.

- [x] **6.3 Municipal CSV inbox** — no migration; `source='municipal'`, the sources row and jsonb `attrs` all already exist. **The municipal import is the first writer to sit in the MIDDLE of the merge policy** (`crowd > municipal > osm`), so it is the one that exercises the ordering in both directions at once: it overwrites an osm-set field but is frozen by a crowd-set one. That is the whole feature — a municipality's registry can correct stale OSM data, but can never clobber the correction a resident made by going and looking — and `lib/src/merge-policy.test.ts` was EXTENDED with exactly those scenarios (municipal-over-osm applies, crowd-over-municipal freezes, municipal revises itself, an unchanged re-import writes nothing).
  - **Dedupe is distance + name, biased so a false CONFLICT is safe and a false MATCH is not.** A registry row has no stable id, so each incoming row is matched against existing facilities by PostGIS distance (the two-stage `ST_DWithin` on the gist index → exact `ST_DistanceSphere`, the crowd add-facility technique) and normalised-name comparison. Auto-match happens ONLY within 40 m with a matching name; a same-spot different-name, a same-name-just-farther, or two candidates on one point all fall to CONFLICT, because a false match silently rewrites the wrong facility while a false conflict just asks a human. `namesMatch` is deliberately not transliteration-folding — a Cyrillic and a Latin name for one place are far more likely to be two records the operator should see than a merge worth making automatically.
  - **Conflicts are resolved per-row, and the resolution is re-checked live.** The preview groups rows new/match/conflict/invalid; each conflict shows the facility it collides with (name + distance) and offers skip / link-to-existing / create-new. The commit RE-CLASSIFIES every row from the database rather than trusting the posted preview (the bulk-create rule), and a `link` to a facility the row is no longer near is refused, not obeyed — so a tampered form post cannot point an update at an arbitrary id. An unresolved conflict is never written.
  - **Through `facility_edits`, like every other writer.** A new row inserts `source='municipal'`, `needs_verification` (a registry entry is a claim to verify, not a confirmed fact), municipality derived by `ST_Contains` at insert, a `created` audit row, and its provenance in `attrs.municipal` (the operator-supplied registry label — provenance on every record). An update runs `mergeFields` and writes one `facility_edits` row per applied field; `actor` is NULL because a registry import is institutional data, not a person's contribution. An updated OSM-origin row keeps `facilities.source='osm'` — that column records where the ROW came from, and per-field provenance lives in `facility_edits.source`, which is what the merge policy reads. `db/src/import-municipal.test.ts` proves the osm-overwrite, the crowd-freeze, the auto-match, the unresolved-conflict no-op, the refused cross-link, and idempotency against a real database in a rolled-back transaction.
  - **`/admin/obshtini`, `requireRole('admin')`** on the page and every action — a registry import rewrites the canonical dataset nationally, exactly like the OSM import, so it is admin-only and not an ambassador's municipality-scoped tool. The forgiving normaliser reads Bulgarian or English enum values and a comma decimal separator, treats an empty lighting cell as unknown rather than false, and rejects a row it cannot place on the map (a facility's geom is NOT NULL; geocoding is out of scope) — the same validation vocabulary as the crowd add-facility flow, so a municipal import cannot write a value a resident could not.

## 9a. Stage 8 — Sustainability (folded in from docs/MONETISATION.md, 2026-07-25)

The plan is `docs/MONETISATION.md`; this is the roadmap's record of what shipped.
One shape holds all of it: **sponsorship is content beside our own, never
surveillance and never authority.** Every table here is off the open-data
`ALLOWED_RELATIONS`, carries no contact-person column (sponsor contacts are
natural persons and live in the offline CRM), and none of them can influence
facility data, moderation or scoring. Migrations `0019`–`0023`.

- [x] **8.1 Partners registry + `/partnyori` + `/podkrepi`** (M1; migration `0019_partners`) — registry with bilingual content columns, admin CRUD, logo upload through the EXIF-stripping webp pipeline, and a row-decides logo route. `/partnyori` renders tier sections with `rel="sponsored noopener"` on every outbound link (selling followed links is a link-scheme violation whose collateral damage would land on the `/igrishta` SEO pages). **`/podkrepi` closed 2026-07-25**: a prose page that takes no money — bank details from the environment (`DONATION_*`, never in git), the донор tax-relief explanation as information rather than advice, and no card widget, because a payment provider's script would be the first third-party script on a cookieless site and would buy a consent banner for the price of a donation button. `DONATION_PAYMENT_URL` is the sanctioned escape hatch: a link OUT to a processor-hosted page. - [x] **8.2 Ad slots** (M4; migration `0021_ad_placements`) — four labelled, direct-sold, first-party-served slots. **The component is the compliance argument**: no client JS, no external request, nothing stored on the device, and selection by SURFACE only — `AdSlot` cannot know who is reading, which is what keeps the site free of consent machinery and the privacy promise true.
